1. 项目概述与架构

ESP32_COMM 是机器人 DCU 板上 ESP32-C3 的通信与 OTA 中枢固件：上位机经 WiFi HTTP / BLE GATT 把固件交给 ESP32；ESP32 自身走 app0/app1 AB 分区升级，GD32E508 固件经 SPI Link v2 六阶段握手 + AES-128 逐包加密中继，电机节点固件再经 GD32 CAN 二次中继；同时提供三路 CANFD 控制面与遥测回收。

[PC / 手机网页]──WiFi HTTP(22 路由) / BLE GATT(0xFFFF)──▶[ESP32-C3FH4]──SPI Link v2 13.33MHz 5线──▶[GD32E508]──3×CANFD──▶[电机节点]
                                                         │ gd32_ota 252KB 缓存            │ Bootloader / APP
                                                         │ app0/app1 AB 自升级            │ 电机 OTA CAN 中继

任务模型：ota_relay(23) · wifi_ota/ble_ota(22) · health_mon(21) · ble_ota_worker(12) · spi_worker(8，唯一持 SPI) · ota_feed(7) · httpd(5) · can_fb(4) · cpu_stats/uart_rx(1)。

2. 评审范围与方法

  • 范围：main/ 全部 60 个 C/C++ 源文件（≈ 2.0 万行）、components/transport、config/、两份 sdkconfig.defaults、sdkconfig.ci、dependencies.lock、CMake 与 Kconfig、CI workflow、.devcontainer/.vscode/.gitignore、Python 工具脚本、README 与白皮书、git 历史。
  • 专家组：① SPI 协议与传输；② OTA 可靠性（协调器 / 本机 OTA / GD32 中继 / 存储 / 电机 OTA）；③ 网络与无线安全（HTTP / WiFi / BLE）；④ FreeRTOS 实时性 + 构建与仓库卫生 + 代码质量。各组独立通读，主审对每条结论回到当前代码二次核对行号（基线 af1f682）。
  • 既有评审：当前树仅有 docs/project_introduction.html §18/§19（含 2026-08-16 安全审计）与 README。git 历史中另有三份已被删除的评审：2026-06-27 架构扫描（af1f682 删除）、2026-06-13 高风险评审与 2026-05-05 通信梳理（5b2c5f8 删除）。本次已原样恢复至 docs/review/archive/，并在第 5 节逐条跟踪。
  • 严重度：致命＝可远程任意控制/变砖/必现崩溃；严重＝特定条件下数据损坏、失联、OTA 失败或明显安全缺陷；一般＝健壮性/一致性缺陷；建议＝可维护性/风格。
  • 局限：未上板实测；仓外依赖 spi_link/spi_link_v2.* 不在本仓库，CRC/帧格式部分只能按调用侧判断；0627 评审中约 50 条低风险风格类 P2 条目未逐条复核；网页前端（tools/）已移出仓库，不在范围内。

4. 问题详情

致命（1）

致命 F-01 · HTTP 全部端点零认证 + CORS * + /spi/send 原始透传 ［安全］

位置
main/server/http_handlers.cpp:77-83, 1685-1756
现象
22 条路由无任何鉴权；所有响应带 Access-Control-Allow-Origin: *；/spi/send 的 frame_type 直接取自请求（strtol），无白名单，经 SpiMaster::transact 原样下发 GD32，绕过 OtaCoordinator 互斥。
风险
同网段任意主机（或用户浏览的任意网页借 CORS 跨站）可上传/切换固件、重启、发 CAN 帧、向 GD32 注入任意 SPI 命令（含进 Boot、擦写类命令），机器人电机总线可被远程操控。
修改建议
最小改造：① 实施已设计的 Bearer token（NVS 存放，首次配网生成）；② CORS 改为白名单来源或去掉；③ /spi/send 加 frame_type 白名单（仅只读诊断类），并在 OTA 忙时拒绝；④ 默认编译期关闭 /spi/send 与 /spi/speedtest。

严重（12）

严重 S-01 · 干净克隆构建出的是另一份固件（关键配置文件未生效且自相矛盾） ［构建］

位置
CMakeLists.txt；sdkconfig.defaults；config/sdkconfig.defaults:7-13,23,34,89-90；.gitignore:33
现象
自定义分区表、4MB Flash、FREERTOS_HZ=1000、APP_ROLLBACK 只写在 config/sdkconfig.defaults，根 CMakeLists 未设置 SDKCONFIG_DEFAULTS，IDF 只读根目录 sdkconfig.defaults；sdkconfig 被 gitignore 未入库。config/ 版本还写着 FLASHMODE_QIO 与 BT_BLUEDROID_ENABLED，与根配置（DIO、NimBLE）冲突。
风险
新环境/CI/同事机器构建得到：单 factory 分区（无 gd32_ota、无 app0/app1，ESP32 自升级不可用）、HZ=100（pdMS_TO_TICKS(1/3/5)=0，SPI 等待退化为零超时/忙让）、无回滚。若有人改为引用 config/ 版本，则 QIO 导致 OTA 读回 SHA 必错。
修改建议
把分区表/Flash 大小/HZ/回滚并入根 sdkconfig.defaults，删除或标注废弃 config/sdkconfig.defaults；代码中加 static_assert(configTICK_RATE_HZ == 1000)；CI 增加一次 idf.py build 并校验分区表。

严重 S-02 · 回滚保护取消过早：mark_app_valid 早于自检判定 ［OTA］

位置
main/core/main.cpp:131-147
现象
esp_ota_mark_app_valid_cancel_rollback() 在 SystemBoot::report() 之前无条件调用；随后若 critical_ok 为 false 才 3 秒后 esp_restart()。
风险
新固件关键初始化失败（SPI/WiFi/HTTP 起不来）时已被标记有效，重启后仍运行坏固件，回滚机制形同虚设；在仅能网页升级的现场即“软变砖”。
修改建议
先 SystemBoot::report()，仅 critical_ok 才 mark valid；更稳妥是在 WiFi/HTTP 可达且 SPI L0 通过后（或前端确认后）再 mark，失败时 esp_ota_mark_app_invalid_rollback_and_reboot()。

严重 S-03 · 看门狗/中止路径与中继任务并发：清会话密钥但中继任务不停 ［并发］

位置
main/ota/ota_coordinator.cpp:625-635；main/relay/ota_relay.cpp:539-554
现象
doAbortLocked 在 httpd 任务内、持协调器锁调用 OtaRelay::abortRemoteAndReset(true)，其 reset() 清零 m_kSession / m_nonceServer、解除 ring 抑制；而 ota_relay 任务中的 forwardFirmware 没有任何取消标志，仍在用这些数据收发 SPI。OTA_RESULT_ERR_USER_ABORT 从未被触发。
风险
中继后续包以全零密钥加密发往 GD32、两个任务同时发 CANCEL/数据，GD32 半会话残留；与 S-04 叠加时在慢速但合法的中继中可复现。
修改建议
引入 std::atomic<bool> 取消标志 + 事件组：abort 只置标志并等待中继任务自行收尾（带超时），reset() 只能由中继任务自身调用；协调器不在持锁状态下做 1.5 s 级 SPI 操作。

严重 S-04 · 忙态看门狗 150 s 短于 GD32 中继合法最坏耗时 ［OTA］

位置
main/include/app_config.h:126；main/relay/ota_relay.cpp:361-368
现象
OTA_COORD_BUSY_WATCHDOG_MS=150000；传输阶段自身预算上限 120 s，且只从 TRANSFERRING 开始计；进 Boot(2×12 s+HELLO)、握手 20×1.6 s、SIZE_NEG 最多 120×500 ms、FINISH 10 次+APP 存活轮询都在预算之外。
风险
接近满尺寸固件或总线繁忙时，本可成功的中继会被看门狗中止（并触发 S-03 的并发问题），表现为偶发“OTA 卡在 9x% 后失败”。
修改建议
看门狗改为按阶段续期（中继任务每阶段/每 N 包喂狗），或将阈值设为各阶段上限之和 + 裕量；统一由中继任务上报进度时间戳。

严重 S-05 · WiFi 运行期断线重试 5 次后永不重连，也不回退 AP ［健壮性］

位置
main/server/wifi_ota.cpp:94-100, 180-192, 751-777
现象
重连任务达到 WIFI_STA_MAX_RETRY 后 setStaRetryExhausted(true)；该标志只在 STA_START/CONNECTED/初始化时复位（156/168/291 行），断线事件在 exhausted 时不再唤醒重连；AP 回退只在开机流程中执行。
风险
路由器重启或短暂断电超过几次重试窗口后，设备永久失联，只能现场断电；HTTP/OTA/CAN 控制全部不可用。
修改建议
耗尽后改为长周期退避（如 30 s~5 min）持续重连，或运行期回退 AP+STA 并行；同时把耗尽状态纳入 /system/status 与健康监控。

严重 S-06 · GD32 握手 nonce 可预测且时间戳明文入日志 ［安全］

位置
main/relay/ota_relay.cpp:1027-1035；main/transport/protocol.cpp:90-131
现象
nonce_server = scrambleGenerate(xTaskGetTickCount(), &m_nonceServer, 0x12345678)；种子为常量、地址固定，按字节映射使同一次开机内 nonce 第 4~15 字节恒定，仅 4 字节 tick 变化；tick 以 DEBUG_INFO 明文打印（并经 UDP 广播到局域网）。
风险
会话密钥 K_session = AES(MASTER_KEY, nonce) 的新鲜性只剩 32 bit 且可从日志获知，配合硬编码 MASTER_KEY（S-08）可离线复现会话密钥、重放或伪造 OTA 数据。
修改建议
16 字节全部取自 esp_fill_random()（确保 RF 已开或 bootloader_random_enable）；删除 timestamp 日志；scrambleGenerate 仅保留为兼容路径。

严重 S-07 · GET /can/mode 查询失败时会把 CAN 接收模式写回 ALL_PASS ［健壮性］

位置
main/server/http_handlers.cpp:1020-1030
现象
0xC1 查询失败的回退路径调用 canFdSetRxMode(CAN_RX_MODE_ALL_PASS, &actual, 2000) 作为“查询”，这是一次写操作。
风险
前端轮询 GET 一次失败即静默把用户设定的 FILTER / CAN0→1/2 BRIDGE 模式改回全收，电机总线桥接中断，且无日志可见。GET 有副作用也违背 HTTP 语义。
修改建议
增加只读查询命令（或复用 0xC1 重试），失败时返回 {ok:false} 与缓存值，绝不写入。

严重 S-08 · 凭据与主密钥明文入仓，AP 弱口令 ［安全］

位置
main/include/app_config.h:31-32, 39-40, 161-164；main/server/wifi_ota.cpp:264
现象
STA SSID/密码（真实口令）、AP 密码 12345678（WPA/WPA2 混合）、MASTER_KEY = 01 23 45 67 89 AB CD EF FE DC BA 98 76 54 32 10（示例向量）均为源码常量，且已进入 git 历史。
风险
仓库任何读者可接入现场 WiFi 与设备 AP；MASTER_KEY 公开即 GD32 挑战-应答与逐包加密全部失效，可向 GD32 注入任意固件。
修改建议
迁移到 NVS（出厂配置写入）或 Kconfig + 不入库的 sdkconfig；轮换已泄露的 WiFi 口令；每设备派生密钥（MASTER_KEY ⊕ UID KDF）；CI 加 gitleaks 扫描。

严重 S-09 · BLE GATT 无配对/加密，范围内任意设备可 OTA 或重启 ［安全］

位置
main/server/ble_ota_host.cpp:366-376
现象
CTRL/DATA_IN 特征仅 BLE_GATT_CHR_F_WRITE / WRITE_NO_RSP，未要求 WRITE_ENC/AUTHEN，未配置 SM。
风险
10~30 m 内任意手机可发 0xFA 重启、0xFB 中止、上传固件触发 GD32 中继。
修改建议
启用 LE Secure Connections（Passkey 或 OOB），关键特征加 BLE_GATT_CHR_F_WRITE_ENC | WRITE_AUTHEN；或至少在 CTRL 上加应用层 token。

严重 S-10 · RSSI 更新覆盖过温 SAFE_SHUTDOWN 健康状态 ［实时性］

位置
main/monitor/health_monitor.cpp:578-600；main/server/wifi_ota.cpp:853
现象
温度与 RSSI 共用 m_healthState；updateFromWifiRssi 只要 next != cur 就 setState(SYS_NORMAL/WARNING/CRITICAL)，会把温度路径设置的 SYS_SAFE_SHUTDOWN 改写掉。
风险
过温门控被下一次 RSSI 采样清除，高温下仍允许启动 OTA（Flash 擦写 + 射频满负荷），存在硬件损伤与写坏风险。
修改建议
拆分温度/RSSI 子状态，整体状态取两者最严重值；SAFE_SHUTDOWN 只能由温度路径解除。

严重 S-11 · 栈溢出钩子中调用可阻塞的 uart_write_bytes ［实时性］

位置
main/monitor/task_stack.cpp:27-40
现象
vApplicationStackOverflowHook 运行在 vTaskSwitchContext（调度器临界区）内，却调用带互斥锁、可能阻塞的 uart_write_bytes。
风险
溢出发生时可能在钩子内死锁/二次异常，丢失现场信息，甚至无法走到 esp_system_abort。
修改建议
改用 esp_rom_printf / ets_printf（ROM 直写），或只置标志后立即 abort，由 panic handler 输出任务名。

严重 S-12 · /spi/send 的 timeout_ms 无上限，可长期占死 SPI worker ［安全］

位置
main/server/http_handlers.cpp:1715；main/transport/spi_master.cpp:646
现象
